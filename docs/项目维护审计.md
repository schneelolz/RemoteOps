# RemoteOps 项目维护审计

- 审计日期：2026-08-05
- 审计范围：Workspace 结构、Cargo 包职责、文档入口、发布产物和维护热点
- 结论：目录架构合理，不建议为了形式改成通用 `src/<project>`；当前优先治理文档事实来源、发布物边界和超大壳文件。

## 一、本次已完成

- 建立唯一文档入口，并按安装使用、部署验收、维护交接和历史依据分类。
- 新增项目结构、文档维护、发布产物说明和文档链接自动检查。
- 标记第一阶段报告和固定三机手册为历史/实验资料，避免误用为公网参数。
- 恢复 `docs/history/evidence/lab-e2e-result-2026-07-31.json` 规范链接，并记录历史运行标识与 SHA-256 不一致问题。
- 迁移前内部版本曾分别使用 Agent `2.3.1`、MCP `2.2.0`、Relay/其他控制端 `2.1.0` 和开源准备版 `4.1.0`；这些编号只保留为历史依据。
- 当前公开版本统一从 `0.2.0-preview.1` 开始，串口 Demo 保留独立的 `0.5.0` 验证编号；已移除私人 Relay 默认值和预编译 Docker artifact 依赖。

## 二、结构判断

现有 `apps / crates / tests / deploy / scripts / docs` 符合 Rust Workspace 的职责划分。核心业务已经集中在类库，CLI、MCP 和 GUI 主要作为壳子复用应用服务。本轮不移动代码项目，不制造大量 Cargo 路径和部署脚本变更。

## 三、维护热点

| 文件 | 当前规模 | 建议 |
|---|---:|---|
| `apps/remoteops-controller-gui/src/main.rs` | 约 3400 行 | 后续按页面状态、窗口、对话、主题拆分模块，保持 UI 状态不进入核心业务 |
| `apps/remoteops-relay/src/relay.rs` | 约 3100 行 | 后续按注册/配对、转发、审批、恢复、持久化拆分内部模块 |
| `apps/remoteops-controller-gui/src/backend.rs` | 约 2600 行 | 后续按连接、审批、AI、串口和文件用例拆分 |
| `apps/remoteops-agent/src/lib.rs` | 约 2400 行 | 后续按配置/状态、传输、请求执行和设备发现拆分 |
| `scripts/Invoke-LabE2E.ps1` | 约 2000 行 | 后续拆成环境、部署、用例和清理模块，保持单一编排入口 |
| `apps/remoteops-controller-mcp/src/main.rs` | 约 1500 行 | 后续把输入输出模型、工具路由和结果转换拆分，业务仍留在应用层 |

这些文件目前测试通过，不应在真实试点前一次性大重构。建议每次只拆一个边界，保持行为和公共参数兼容，并先补对应测试。

## 四、产物治理发现

- `artifacts` 已被仓库级 `.gitignore` 排除，只保留当前版本的统一 Release 和独立自有 Relay 测试配置。
- 正式分发入口只引用 `artifacts/release/<版本>` 下的 `windows-x64`、`linux-x64`、`mcp` 和 SHA-256 清单。
- 历史产物、截图、实验日志和临时安装验证目录不进入当前保留清单；需要长期保留的脱敏结论进入 `docs/history/evidence`。
- 当前 Windows 内部产物未做 Authenticode 签名，这是扩大分发前的发布门禁，不是代码功能缺陷。

## 五、后续建议顺序

1. 完成真实低权限 Windows + 独立 Human Controller 现场验收。
2. 确认代码签名证书、安装包发布渠道和升级策略。
3. 建立 `artifacts` 保留清单，清除纯临时日志和安装验证目录。
4. 先拆分 Controller GUI `backend.rs` 或 MCP `main.rs`，一次只处理一个模块。
5. 将三机脚本拆分为内部模块，并让结果文件记录版本、运行标识和自身哈希来源。
