# 提交与CI检查约定

更新日期为2026年11月10日。提交、推送及清理前读取本文件，并核对当前工作流实际配置。

## 提交前检查

1. 分别记录仓库分支、HEAD、工作区差异、已有暂存内容和未跟踪文件。只暂存已审查的本次文件，保护配置、凭据、交付和用户改动。
2. 读取 `.github/workflows/ci.yml`、`docs.yml` 及本次相关工作流，按文件范围运行适用检查。文档改动执行 `scripts/Test-Documentation.ps1` 和 `git diff --check`。
3. 检查文档中的本机绝对路径链接。仓库内链接使用相对路径，跨仓库资料使用已推送提交的URL，私有本机运行手册使用文字名称。
4. Rust实现先运行相关测试、格式和严格Clippy，再按影响运行工作区及跨平台CI。Windows本机通过后仍需核对Linux、macOS与MSRV结果。
5. 发布构建与占用同一EXE的浏览器、TCP夹具、Agent进程串行安排，避免Windows文件占用造成重复构建。长临时路径检查使用短根目录，并按测试实际退出码及结构化报告判断结果。

## 推送与CI确认

- 推送前核对分支触发过滤及路径过滤。目前公共CI的push自动触发范围为main与codex/public-product-separation，Documentation的push范围为main。其他工作分支需通过PR触发或对正确分支执行workflow_dispatch。实际配置变化时以工作流为准。
- 推送后记录完整提交SHA，查询该SHA的工作流。零条检查记录时继续确认触发入口。
- 对获授权的代码提交可使用 `gh workflow run ci.yml --ref <当前分支>`，文档使用 `gh workflow run docs.yml --ref <当前分支>`。等待并核对对应headSha、run id、各job及最终conclusion。
- CI失败时先提取首个失败步骤和相关日志，区分实现、测试假设、平台、编码、依赖或运行环境问题。修复后先跑最小复现，再扩大验证并推送。
- 适用工作流全部成功后报告CI通过。排队、未触发、取消、运行环境缺失、仅本地成功或其他提交成功分别记录。
- 汇报耗时分别列出本地构建、CI排队、CI执行和修复重跑，维护记录附实际run链接。

## 清理约定

- 清理前列出明确绝对路径、用途、数量和大小，检查目标位于允许的工作区或已明确的临时根目录，拒绝链接、越界和未确认路径。
- 生成缓存可删除。浏览器截图、测试日志及失败复现材料先归档并核对摘要，再清理工作目录副本。
- 正式交付、源码快照、锁文件、许可证、发布摘要、可恢复备份、配置凭据和仍在使用的进程路径予以保留。
- PowerShell原生删除与移动使用 `-LiteralPath`，操作前核对解析后的绝对目标。Git操作不承担临时文件清理职责。
