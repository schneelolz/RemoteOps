# RemoteOps 项目结构规范

## 一、架构原则

RemoteOps 采用“核心业务唯一实现，多个壳子复用”的 Rust Workspace。业务规则进入 `crates`，可执行入口只负责参数、界面、宿主生命周期和输入输出，不在 CLI、MCP 或 GUI 中复制策略。

## 二、目录职责

```text
remoteops
├─ apps        可执行程序：Agent、Agent Service、Relay、Controller、MCP、GUI、Demo
├─ crates      领域、协议、策略、设备、审计、会话和应用服务
├─ tests       跨组件自动化验收工具
├─ deploy      Relay、Agent Service 和 Windows MCP 的部署/安装材料
├─ scripts     构建、发布、实验和回归入口
├─ docs        当前手册、维护说明和历史验收资料
├─ build       Windows 资源等仓库级构建辅助
├─ artifacts   生成的发布文件和验收结果，不作为源码
└─ target      Cargo 构建缓存，不作为交付物
```

## 三、可执行项目分类

| 项目 | 角色 | 是否独立发布 | 主要职责 |
|---|---|---|---|
| `remoteops-agent` | 现场运行时与 CLI 壳 | 是 | 主动连接 Relay、上报能力、执行设备操作；GUI 复用其运行时 |
| `remoteops-agent-gui` | Windows 被控端 GUI | 是 | 零参数启动、控制码、状态、能力展示和停止入口 |
| `remoteops-agent-service` | 可选 Windows Service 宿主 | 是 | 注册 SCM 生命周期、复用 `run_agent()`、提供短期状态文件；不复制业务规则 |
| `remoteops-relay` | Linux 服务 | 是 | TLS 长连接、注册、配对、会话转发、角色认证、审批和状态持久化 |
| `remoteops-controller-cli` | 人工/自动化 CLI | 是 | 配对、诊断、审批、事件和文件操作的命令行入口 |
| `remoteops-controller-mcp` | Codex STDIO MCP | 是 | 把 MCP 工具调用映射到核心应用服务，不自行实现策略 |
| `remoteops-controller-gui` | Human Controller GUI | 是 | 人工接管、审批、终端、串口工作台和 AI 辅助界面 |
| `remoteops-serial-demo` | 本地验证工具 | 是 | 不经过 Relay，直接验证真实 COM 和 AI 交互 |
| `remoteops-mcp-smoke` | 自动化验收工具 | 否 | 使用官方 Rust MCP SDK 验证工具注册和端到端行为 |

## 四、核心类库分类

| 类库 | 职责边界 |
|---|---|
| `remoteops-domain` | ID、能力、操作、事件、审批等领域模型和不变量 |
| `remoteops-protocol` | 线协议消息、帧、TLS 和协议版本 |
| `remoteops-session` | 多连接注册、别名、编号、解析和角色绑定 |
| `remoteops-policy` | 只读判定、风险分类和审批策略 |
| `remoteops-audit` | 脱敏、哈希、JSONL 审计和导出 |
| `remoteops-device` | Shell、文件、TCP、SSH、串口等系统能力适配 |
| `remoteops-serial` | 串口终端、记录、分页、结构化查询、授权和脱敏 |
| `remoteops-application` | Controller 用例编排、Relay 客户端和跨壳共享服务 |
| `remoteops-ai` | OpenAI 兼容接口、工具调用和 AI 上下文适配 |
| `remoteops-i18n` | 内置中英文、系统语言检测和安全外部语言包覆盖 |

核心类库不得依赖 GUI 控件、CLI 参数格式或具体宿主生命周期。壳子可以依赖核心类库，核心类库不能反向依赖壳子。

## 五、代码放置规则

- 新业务规则优先放入职责匹配的 `crates/remoteops-*`。
- 新宿主或表现层放入 `apps/remoteops-*`，并调用核心应用服务。
- 跨组件自动化验证放入 `tests`；单元测试与被测模块同项目维护。
- 部署模板、Compose、安装包源文件放入 `deploy`；可重复构建脚本放入 `scripts`。
- 生成物只进入 `artifacts`，不得把 Token、私钥或运行状态打入发布包。

## 六、版本规则

可独立发布的 EXE 分别维护版本。修改并重新分发某个 EXE 时必须升级该项目版本，并核对 Cargo 版本、Windows 文件版本、产品版本和发布清单一致。共享类库的兼容变更不应机械抬升未重新发布的其他 EXE。

首个计划公开版本为 `0.2.0-preview.2`；当前 Workspace 源码版本为 `0.2.0-preview.2`。公开版本和源码候选版本必须明确区分，不得在尚未创建 Release 时宣称已公开。产品版本变化不改变线协议版本；当前协议为 v12。

## 七、变更同步

新增、删除或移动功能代码时，同步更新：

1. `docs/功能索引.md`；
2. `docs/README.md` 的用户入口；
3. 对应安装、部署或使用手册；
4. 发布产物版本、SHA-256 和清单；
5. 相关自动化测试与验收步骤。
