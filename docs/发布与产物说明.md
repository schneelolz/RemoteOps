## 目录边界

| 路径 | 内容 | Git 策略 |
|---|---|---|
| `target` | Cargo 编译缓存 | 忽略，可重新生成 |
| `artifacts/release/<版本>/windows-x64` | Windows EXE 与构建清单 | 忽略，由统一发布脚本生成 |
| `artifacts/release/<版本>/linux-x64` | Linux Relay 二进制与清单 | 忽略，由统一发布脚本生成 |
| `artifacts/release/<版本>/mcp` | Windows MCP 安装 ZIP；macOS CI 生成 Apple Silicon tar.gz | 忽略，由发布脚本生成 |
| `artifacts/release/<版本>/SHA256SUMS.txt` | 全部发布文件的统一哈希 | 忽略，由统一发布脚本生成 |
| `docs/history/evidence` | 已脱敏且有长期价值的验收摘要 | 可提交 |
| `deploy` | Docker、Compose、Agent Service、安装说明和脚本模板 | 必须提交 |

`artifacts` 可以随时清空。它不是事实来源，也不能成为 Docker 源码构建的输入。

## 构建入口

```powershell
.\scripts\Build-Release.ps1 -CleanLegacyArtifacts
```

需要单独构建某个平台时，仍可直接调用 `Build-Windows.ps1`、`Build-WindowsMcpPackage.ps1` 或 `Build-LinuxRelay.ps1` 并显式指定输出目录。

Windows 与 Linux 正式构建脚本默认先清理对应 Release 缓存，避免源码已更新但旧增量对象被误复制到发布目录；仅在明确进行本地增量调试时使用 `-SkipClean`。

Windows 正式构建通过 `-Ctarget-feature=+crt-static` 静态链接 MSVC CRT，现场 EXE 不依赖单独安装的 VC++ 运行库。该设置由 `Build-Windows.ps1` 和 `Build-WindowsMcpPackage.ps1` 统一注入，GitHub Windows Release 复用相同脚本。

正式构建会通过 Rust `--remap-path-prefix` 重映射工作区、用户目录和 Cargo 缓存路径，并由 `scripts/Test-ReleaseArtifacts.ps1` 拒绝仍内嵌本机绝对构建路径的产物。GitHub Release workflow 也执行同一门禁。

Relay 公共镜像必须从 `deploy/relay/Dockerfile` 和当前源码构建。仓库不保留复制本地预编译 Relay 的 Dockerfile。

## GitHub Release

正式发布应包含：

- `RemoteOps-Windows-x64-<版本>.zip`：Windows Agent、Service、Controller、MCP、GUI 和清单；
- `RemoteOps-Agent-linux-x64-<版本>.tar.gz`：Linux 无界面 Agent 和 Service；
- `RemoteOps-MCP-Windows-x64-<版本>.zip`：Codex MCP 独立安装包；
- `RemoteOps-MCP-macOS-arm64-<版本>.tar.gz`：Apple Silicon Mac 的 Codex MCP 独立安装包；
- `RemoteOps-Relay-Linux-x64-<版本>.tar.gz`：Linux Relay；
- `SHA256SUMS.txt`：以上 GitHub Release 资产的 SHA-256；
- 每个归档内的 `LICENSE`、`THIRD_PARTY_LICENSES.txt` 和 `DEPENDENCIES.json`：项目许可证、第三方 SPDX 表达式与上游随包提供的许可证/Notice 文本，以及机器可读依赖清单；
- 对应版本的变更日志。

发布工作流必须从干净检出构建，不能读取开发机已有 `artifacts`。最终资产目录必须且只能包含五个版本化归档和 `SHA256SUMS.txt`；门禁会复算每个归档的 SHA-256，检查归档内法律文件，并拒绝日志、转储、密钥、状态和审计文件。

## 版本核对

每次发布分别核对：

- Cargo 包版本；
- Windows `FileVersion` 与 `ProductVersion`；
- 文件长度和 SHA-256；
- 安装包内 README、脚本和 EXE 的版本一致性；
- Release 标签与 `CHANGELOG.md` 一致。

标签必须精确等于 `v<remoteops-agent 的 Cargo 版本>`，当前为 `v0.2.0-preview.7`。Technical Preview 必须发布为 GitHub prerelease，不能标记为稳定版本。

各组件可独立递增版本。Windows 清单记录每个 EXE 自身的 Cargo 和文件版本，Agent GUI 与 SSH askpass 必须同包，但不要求版本相同。GitHub Release 归档文件名使用统一发布版本，MCP 包内目录和程序保留 MCP 自身版本。

`scripts/Test-ReleaseArtifactGate.ps1` 使用带 Windows 版本资源的测试文件验证独立组件版本和清单校验；CI 与 Release 会在 Linux 和 Windows 构建前运行该回归检查。

## 证书和凭据

- 仓库和发布包不得包含 TLS 私钥、Controller Token、密码、真实控制码、恢复令牌、状态文件或审计日志。
- Agent、Controller CLI/GUI 和 MCP 在未指定 CA 文件时使用操作系统可信根，不分发 `relay-cert.pem`。
- 私有 CA 用户自行提供 `ca_cert`；安装器可以复制用户明确指定的 CA 公钥证书，但绝不能复制私钥。
- Relay TLS 证书由部署者挂载，或仅在开发环境使用 Relay 自动生成的自签名证书。
- Agent Service 默认使用 `LocalService`；`-AllowLocalSystem` 只用于明确的实验环境，不能作为公开部署默认值。
- Service 的 `runtime-status.json` 是短期运行状态，不得进入备份、日志或 Release；卸载默认保留配置和 Agent 身份状态。
